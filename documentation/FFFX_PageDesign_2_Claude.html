Form follows f(x) — Landing Page Concept Broad description Form follows f(x), or fffx, is a Level 1 web-world under the larger Cabinet of Curiosities ecosystem. It is intended to host creative coding, generative art, p5.js experiments, algorithmic sketches, code-driven visual studies, and interactive web pieces. The landing page should itself feel computational and generative. The chosen visual metaphor is a recursive rectangular subdivision field. The page begins with a large rectangular canvas-like area, filling the viewport and potentially extending vertically depending on the number of entries. The layout is generated by recursively subdividing rectangles:

  1. Start with one large rectangle.
  2. Pick a rectangle.
  3. Split it along its longer side.
  4. Choose a semi-random split ratio, constrained so the result does not become too skinny.
  5. Continue recursively until a minimum size, depth, or visual density is reached.
  6. Keep track of rectangles at multiple subdivision levels, not just the final smallest rectangles.

  7. Select appropriately sized rectangles to become thumbnail/link tiles. Some rectangles become actual project thumbnails; the rest remain as decorative filler cells. The result should feel like an algorithmic field, computational map, or generative layout system. The thumbnail/link tiles are real HTML anchor elements, not canvas-only drawings. This ensures that links are accessible, keyboard-focusable, SEO-visible, right-clickable, and easy to maintain. The subdivision field may be built with HTML/CSS elements first; canvas/SVG can be added later only if a dense decorative layer is needed. The page should support:

  8. A title/introduction area: “Form follows f(x)”
  9. A short intro explaining that this is a collection of creative coding and algorithmic visual experiments
  10. Data-driven thumbnail tiles linking to individual projects/pages/repos
  11. Ordered but generative placement
  12. Weighted tile sizes, so some projects are larger or more prominent
  13. Seeded randomness, so the layout remains stable across reloads
  14. Responsive regeneration for mobile, where thumbnails can stack into a vertically scrollable field
  15. Decorative filler rectangles that may later contain subtle patterns, glyphs, code fragments, hatching, tiny animations, or visual noise
  16. Optional future interactions such as local re-subdivision on hover, particles moving inside cells, or a “regenerate layout” button.

The fffx landing page should not be an exhaustive MkDocs-style sidebar. It is a curated visual front door for Level 3 objects: creative coding sketches, generative tools, algorithmic studies, and interactive projects. Some of these objects may live as internal pages in the fffx repo; others may link to separate GitHub Pages repos or older Cabinet writeups migrated into fffx. Design intent The landing page should say, visually: This is a place where code generates form. It should feel algorithmic, but still readable. The weirdness should be in the layout system and background behaviour, not in the basic usability of the links.

The project data lives locally in the fffx repo. A project can appear in multiple landing pages while linking to the same canonical URL. The basic rendering approach:

  1. Load entries from data.js.
  2. Sort entries by order.
  3. Generate a recursive subdivision field using a seeded random generator.
  4. Store rectangles from multiple depths, not just final leaves.
  5. Filter and score rectangles as candidates for thumbnails.
  6. Match ordered/weighted entries to suitable candidate rectangles.
  7. Render selected rectangles as HTML <a> thumbnail tiles.
  8. Render remaining rectangles as decorative filler cells.
  9. On mobile, regenerate with different constraints so at least one thumbnail fits the width and the page scrolls vertically.

Overall data model The fffx landing page should be data-driven. New projects should be added by editing a local data.js file rather than hand-editing HTML. Each entry represents a Level 3 object: an individual sketch, tool, writeup, study, project, or external repo. The data should support:

  • display title

  • ordering
  • visual weight/prominence
  • category/section grouping
  • status
  • tags
  • whether the item is internal, external, migrated, or paired with a repo
  • optional relationship to Cabinet or other worlds

Key fixes in this version:

Subdivision depth — minimum rect sizes are now minW=36, minH=32 (was 110×90), with maxDepth=7. The recursion now runs deep enough to produce a genuinely dense mosaic — you should see many generations of nested cells.

Transparency stacking — each rect's background is rgba(0,0,0, 0.04 + depth×0.045). Because the rects are proper nested DOM nodes (position:absolute inside a position:relative parent), the browser composites them naturally — each generation darkens its parent's colour by drawing semi-transparent black over it. No seven-colour lookup table needed.

Gap between siblings — every child is inset by GAP/2 (1px) on all edges, so siblings share a 2px gutter that's filled by the parent's colour. Clean and consistent at every depth.

Order stability — entries are sorted by weight desc, order asc before matching, and that sort is completely independent of the RNG. The RNG only controls subdivision geometry. So Genuary (weight:3, order:1) always matches before Inktober (weight:2, order:2) regardless of what layout the RNG produces.
